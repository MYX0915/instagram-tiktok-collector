# Instagram 本地采集

使用 Python Playwright、系统 Google Chrome 和网页登录 Cookie，通过网页内 `fetch` 请求作品详情、评论和回复。不模拟点击或滚动。

## 安装与登录

```bash
python3 -m pip install -r requirements.txt
npm install
npm run login:instagram
```

在 Chrome 中手动登录，回到终端按回车。登录脚本保存 `account/instargram.cookies.json`，Python 程序默认复用该文件。必须安装系统 Google Chrome，不需要下载 Playwright Chromium。

## 运行

```bash
python3 instagram.py -link 'https://www.instagram.com/reel/DdO6y3MSSGk/'
```

参数中的链接使用普通 URL，不要包含 Markdown 的方括号和圆括号。

- `--headless`：隐藏浏览器窗口。
- `--cookies /绝对路径/cookies.json`：指定登录脚本导出的 Playwright Cookie 数组文件。
- `--output /绝对路径/目录`：指定输出目录，默认项目下的 `data/instagram`。
- `--max-pages 1000`：每个顶层评论列表、每组回复的分页上限，默认 1000。

输出为 `data/instagram/<作品短码>.json`，同一作品再次运行会覆盖旧文件。

## 输出结构

导出 JSON 使用中文字段名，不添加单独的字段说明表。程序内部仍使用接口原字段，不改变请求、分页或数据值；未知资源字段显示为 `接口字段（原字段名）`，避免丢失。作品、评论和回复的发布时间分别为 `视频发布时间`、`评论发布时间`、`回复发布时间`，均保留 Unix 秒级时间戳；采集开始和结束时间为 UTC ISO 8601 字符串。

| 字段 | 内容 |
|---|---|
| `作者信息` | 详情响应中的作者基础信息，未返回字段为 `null` |
| `视频信息` | 作品 ID、短码、文案、发布时间戳、时长、视频和封面资源 |
| `互动数据` | 点赞、评论、再发布计数，缺失值不填零 |
| `播放量数据` | 播放量、Instagram 播放计数、浏览计数和来源接口 |
| `评论列表` | 顶层评论，包含评论者信息、内容、时间、点赞、父评论 ID 和回复列表 |
| `采集状态` | 评论采集状态、实际条数、未完成阶段与原因 |

先从短码计算媒体数字 ID，再核对详情响应的 `pk`、`code`，不依赖主页列表。作品 ID 保留为字符串。GraphQL 请求使用当前网页的会话信息，不硬编码登录 Cookie 或 CSRF 令牌。

评论通过接口游标持续翻页；有回复的评论继续请求回复。`采集状态.评论是否采集完成` 仅表示当前接口可访问列表的分页完成，不保证包含被删除、被隐藏或当前会话不可访问的内容。详情返回评论数为零时直接记录空列表；其他情况下缺少分页状态、游标重复、接口失败或达到上限均标记未完成。退出码 `0` 表示上述评论流程完成，`2` 表示保留部分结果，`1` 表示运行失败。

作者资料通过 `PolarisProfilePageContentQuery` 单独请求，核对返回用户 ID 后补齐简介、粉丝数、关注数、作品数、高清头像及公开账号类别等。未返回的字段保持 `null`；作者请求失败不丢弃作品和评论结果，记录在 `采集状态.作者资料采集状态` 和 `未完成原因`，最终退出码为 `2`。

评论者和回复者也通过同一公开资料接口补充信息，按用户 ID 去重，每个用户只请求一次；如果用户就是作品作者，复用已取得的作者资料。结果写入对应的 `评论者信息` 或 `回复者信息`，每条评论或回复附带 `用户资料采集状态`，总览位于 `采集状态.评论区用户资料采集状态`。请求失败保留用户摘要；HTTP 401、403 或 429 时停止后续用户资料请求，不循环重试。用户资料未全部补齐时退出码为 `2`，不改变评论分页完成状态。

回复首次请求结构与非空 `after` 翻页兼容，但非空回复游标路径仍需真实平台样本验证。站点变更可能导致 GraphQL 文档 ID、响应节点或页面令牌读取方式失效，此时结果不得当成完整评论。

作品详情先落盘，评论流程结束后再次保存；中途强制退出时文件可能只含先前的详情快照，不提供断点续传。

## 本地检查

```bash
python3 -m unittest discover -s tests -v
```

测试通过本地 HTTP 服务与真实系统 Chrome 执行网页 `fetch`，不使用 Instagram Cookie，不向平台发送请求。组合样本改编自用户提供的详情、评论和回复响应：作品与评论原本不是同一条作品，分页游标和结束状态经过本地测试改写，不作为真实平台当前状态的证据。

字段与抓包依据见 [响应字段文档](docs/instagram-response-fields.md)。

## TikTok 登录准备

```bash
npm run login:tiktok
```

程序打开系统 Chrome 的 TikTok 登录页。手动完成登录，确认已登录后回到终端按回车，将该站点 Cookie 保存到 `account/tiktok.cookies.json`，然后关闭浏览器。该步骤不自动验证登录有效性，不打印 Cookie 内容。

已有 Cookie 时可直接运行：

```bash
python3 tiktok.py -link 'https://www.tiktok.com/@melimakesfaces'
```

默认显示系统 Chrome，在进入主页前注册响应监听，读取主页内嵌作者资料，直接使用匹配作者的首批 `/api/post/item_list/` 自然响应，不再次发送首批请求。未捕获首批或自然响应为空时记录未完成，不通过重复请求假装修复。后续未取得的作品页、评论及回复仍通过网页内 `fetch` 主动请求，不模拟点击或滚动。

- 默认不限制作品数量：按普通作品列表持续翻页，直到接口明确返回 `hasMore=false`，按作品 ID 去重，包含置顶。
- `--limit 50`：可选，手动限制为前 50 个去重作品；不指定则采集全部当前可访问作品，接口顺序不等同于发布时间排序。
- `--headless`：不显示 Chrome 窗口。
- `--debug`：强制有头模式，进入主页后执行 `page.pause()`；在 Playwright Inspector 点击 Resume 才继续采集。优先于 `--headless`。
- `--manual-pauses N`：限制有头模式接口异常时的人工暂停次数，默认不限制，`0` 禁用。手动处理验证码或登录问题后在终端按回车，仅重试当前请求一次；重试仍失败则停止网络请求。无头模式不等待输入。
- `--cookies /绝对路径/cookies.json`：指定 Playwright Cookie 数组文件。
- `--output /绝对路径/目录`：结果根目录，默认 `data/tiktok`。
- `--max-pages 1000`：可选，手动设置每个列表的分页上限；默认不限制页数。
- `--check-reply 作品ID 评论ID`：从已有作品文件读取预览与展开核对记录，只发送一次 `cursor=0,count=3` 的回复对照请求。不自动重试，不重新采集作品、顶层评论或其他回复，不覆盖作品文件或索引。结果保存到 `data/tiktok/_diagnostics/<评论ID>-cursor-zero-control.json`；成功表示取得对照响应，不表示原作品已完整采集。
- `--check-reply-count 20`：仅在 `--check-reply` 模式改变请求条数，允许1至100，默认3。非默认条数的对照文件名包含 `-count20` 等标记，不覆盖默认条数的核对记录；不改变正常采集的请求条数。
- `--retry-incomplete`：只补采当前账号已有 `index.json` 中标记未完成的作品；不主动重取作品列表，不修改已完成作品文件。更新处理过的作品及索引状态。不能与 `--limit` 或 `--check-reply` 同时使用；若网络停止，尚未处理的文件保持原样。

仅核对某条评论：

```bash
python3 tiktok.py -link 'https://www.tiktok.com/@melimakesfaces' \
  --check-reply 7677326215971097887 7689322928077570846
```

输出结构：

```text
data/tiktok/melimakesfaces/
├── index.json                 账号资料、作品文件清单和采集状态
├── 7677326215971097887.json    一个作品及其评论、回复和评论者摘要
├── 7697054890983443743.json    另一个作品的独立数据
└── …
```

每个作品文件均使用中文字段，包含作者信息、视频信息、互动数据、播放量、评论列表、采集状态。评论及回复分别保留 `评论发布时间`、父评论 ID 和直接回复目标 ID；当前统一以评论条目结构表示回复。发布时间为 Unix 秒级时间戳，视频时长原样保留样本中的秒数。评论预览与展开回复按 ID 合并，保留回复计数差异。评论者及回复者仅保留评论接口自带的用户 ID、用户名、昵称、头像等摘要，不额外请求他们的主页或详情接口；未返回的字段保留空值，不补成零。作品作者资料仍保留。

顶层评论每页请求 `count=20`。展开回复每页请求 `count=3`，首个游标统一为 `0`，不根据预览条数偏移；预览回复不保证处于展开列表开头。后续严格使用响应的 `cursor`。预览已覆盖明确的回复计数时不重复请求；展开返回的条数不单独与总数比较，而是先与预览合并、去重后再判断。`has_more=0` 但合并结果仍少于计数时记录数量差异，不解释为验证码。

预览和展开核对信息直接保存到作品 JSON：每条顶层评论的 `预览回复ID列表` 保存预览来源；`回复采集状态.各页响应核对` 保存请求游标、请求条数、每页原始返回 ID、响应游标、分页标记和合并后数量。`合并后回复ID列表` 用于核对去重，`未取得的直接回复目标ID列表` 记录回复引用了但本次没有取得的目标；引用缺失本身不证明该评论已删除或接口漏数。

回复接口可能回显当前根评论：仅当条目 `cid` 等于请求的根评论 ID、`aweme_id` 与 `reply_id` 均等于当前作品 ID，且没有直接回复目标时，将其记入 `排除的根评论回显`，不当作子回复保存，也不生成自回复。其他作品或父评论 ID 不匹配仍拒绝合并。分页结束后若实际子回复条数与计数不同，继续按数量差异警告记录，不宣称不存在或已删除的回复内容。

默认只在接口明确返回列表结束时正常停止作品分页；指定 `--limit` 时，也可在达到该数量后结束。索引中的 `作品数量上限: null` 表示不限制作品数量。作品、评论和回复默认均不限制页数；仅显式指定 `--max-pages` 时才设置分页上限，触及该上限会标记未完成，不会当作已取完。业务失败、HTTP 错误、空响应、重复游标、达到分页上限均不视为成功结束。网络请求失败或超时、HTTP 200 空正文及 HTTP 429/500/502/503/504 时，先等待 5 秒自动重试当前请求一次；服务端 Retry-After 要求更长等待时遵守该时间。自动重试仍失败后，有头模式若尚有人工暂停次数，则保存当前作品进度并暂停；人工在终端按回车后仅重试当前请求一次，明确打印重试成功或失败。作品、评论或回复请求重试失败或暂停次数用尽后停止主动网络请求；无头模式不等待输入。HTTP 401/403、业务状态失败（含状态码 5）、格式或身份校验失败不自动重试。主页自然捕获的首批响应不主动重放；专用回复对照模式仍只请求一次。每个普通请求最多一次自动重试和一次人工确认重试，不伪造签名或循环重试。退出码 `2` 表示未完整取得数据，`1` 表示运行失败。JSON 的分页完成标记不保证包含删除、隐藏或当前会话不可见的内容。

完成状态只检查当前接口可访问的作品列表与评论、回复采集流程，不要求补齐评论者主页资料。索引和作品状态中的 `评论者主页资料采集.是否启用` 为 `false`，不再用资料缺失判断作品未完成。评论或回复请求失败、分页未结束、游标异常或达到分页上限仍记录未完成；接口成功且分页结束时，单纯的回复计数差异只作为警告保留，不改变完成状态，也不保证包含不可见或历史回复。

每条评论的 `回复采集状态` 分别保存 `回复分页是否完成`、`已采集回复数`、`顶层评论回复计数`、`回复接口总计数` 和 `数量是否一致`。未知计数保留 `null`，不补成零；存在差异时保存 `返回数量差异`，实际请求失败的 `未完成原因` 不会被数量差异覆盖。预览已覆盖计数、无需展开时保留相应结束原因。作品状态和索引条目中的 `存在回复计数差异` 汇总警告，索引中的 `回复计数差异作品数` 记录涉及多少作品。流程完成但有差异时退出码仍为 `0`，终端额外提示差异数量。

公共参数仅从已支持的数据接口提取，并按接口保留；网页应用身份参数固定为已确认的 `aid=1988` 等值，避免其他接口覆盖。

失败请求及人工重试失败都会直接在终端打印脱敏请求与响应摘要，无需额外参数：请求包含 GET 方法、接口路径、页面路径与白名单业务参数；响应包含 HTTP 状态、正文字符数、内容类型、跳转状态和业务状态字段。空正文显示 `<空正文>`。非 JSON 错误页提取可读文本，移除脚本、样式与标签，脱敏 URL、常见令牌字段与长标识后最多显示 1200 字符，用于检查 403 等错误的实际说明。其他 JSON 字段及非数字业务消息不输出。终端摘要不等于完整响应抓包，分享前仍应检查是否含个人信息。

正常重跑时覆盖同名作品与索引文件，不清理目录中历史作品；以本次 `index.json` 的文件清单为准。`--retry-incomplete` 仅补采索引内未完成作品，其评论分页从首批开始并按 ID 合并已有条目，不是从原游标继续；已完成作品不改写。程序不自动跑遍 `targets.json` 中全部账号，当前每次指定一个主页。

本地 HTTP 样本测试已覆盖不限数量跨越 50 条并在接口结束时停止、显式数量截断、首批自然响应复用且不重复发送请求、首批未捕获时不重发、后续分页、独立文件保存、评论与回复关联、不请求评论者主页、保留用户摘要和空响应停止。真实平台的作品列表、评论和回复是否完整，以各次运行的索引与作品采集状态为准；不能把本地测试通过当成平台全量采集成功。接口错误记录数字业务状态码或状态字段缺失，不输出响应原文和凭据；回复数量差异独立保存，不覆盖原始失败原因。

TikTok 目标账号仍保存在 `targets.json` 中，按 Snidin、DCXC、AVEYA 分组。

主页作者资料、Story 列表与推荐账号响应的字段及样本见 [TikTok 响应字段与采集规则](docs/tiktok-response-fields.md)。

接口返回 `status_code=5` 时，记录业务失败并等待人工检查，不据此断定页面已出现验证码。只有实际看到验证提示时才手动处理；没有提示时检查目标作品的评论与回复请求。默认运行不需要 Inspector：在 Chrome 检查后，回到终端按回车重试当前请求一次。`--debug` 仍保留启动时的 Inspector 暂停，仅用于显式调试。
